# 银行音频：先大类，再办理业务

用户提出的两阶段流程更贴合业务：每个节点只做一个选择，咨询无需输出办理功能。预留后续第三类（例如需澄清），办理目标不确定时也不强制猜功能。本轮只测已有明确二类core用例，不代表取消、人工、歧义和无语言输入已经处理完成。

## 流程与必要澄清

```
原始用户输入 → 咨询／办理
                 ├─ 咨询 → 问答流程
                 └─ 办理 → 具体业务选择 → 功能导航
```

第二层收到原始用户输入和办理专用题目，候选仅为10类办理功能及unknown。只有第一层实际预测navigate且没有错误才触发；不使用真值决定分支。unknown表示目标未能确定，不能当作成功导航。

需要纠正原测试的解释：固定d05706b源码中，`server_decision_context::is_joint()`只对CLEF成立，LFM3每个question创建独立任务，模板只渲染当前题。原请求虽然带两道题，**底层原本就是两次独立前向，不是一次复合生成**。因此不能把音频低分直接归因于同时生成两个答案。

原先“两题都正确”的指标还要求咨询也识别具体功能；它不等于本流程的最终路由正确率。本轮对旧设置也按同一业务口径重新计分，不把原36.72%与新分数直接对比。

## 固定实验

- 同一份banking-audio-v1的100条core语义用例，50办理、50咨询；100文本和两声线200干净音频。未更改原数据、标签或音频。
- 第一题与上一轮二分类诊断完全一致。第二题改为办理专用问题，保存于`questions.json`。模型仍为d1-Omni-2B Q8_0、同一projector和原生server；环境见`environment.json`。
- 真实串联先跑完300条路由，再对第一层漏掉的真实办理补做业务识别oracle诊断。oracle不回填真实路由结果。
- 实际请求为300次第一层＋140次实际第二层＋18次额外oracle＝458次；零请求错误。`oracle-navigation.jsonl`的150条中132条复用实际业务调用，并非又做150次推理。
- 全部数据已有前轮结果，本轮是架构／题目敏感性诊断，不是新收集的独立泛化验证；业务题措辞和候选描述也变了，不能将变化全部归因于串联本身。

## 结果

最终路由正确的定义：咨询进入咨询分支即可；办理必须大类与目标业务都正确。以下不包含任何oracle补救。

| 指标 | 文本 | 音频，两条件合计 |
|---|---:|---:|
| 第一层咨询／办理 | 100/100＝100% | 174/200＝87% |
| 最终路由正确 | 100/100＝100% | 135/200＝67.5% |
| 真办理完成正确导航 | 50/50 | 43/100 |
| 咨询误闸入办理分支 | 0/50 | 8/100 |
| 咨询最终得到已知业务目标 | 0/50 | 3/100 |
| 真办理在第一层被遗漏 | 0/50 | 18/100 |
| 真实办理业务oracle诊断 | 50/50 | 48/100＝48% |

实际音频业务分支有90次调用，其中82次是真办理、8次是误闸入的咨询。业务标签本身44/90次匹配原标签，但其中1次来自误闸入的咨询；因此真实正确导航只有43次。不能把44/90当成端到端成功率，或忽略先前18次办理遗漏。

| 合成条件 | 第一层 | 真办理业务oracle | 最终路由 |
|---|---:|---:|---:|
| Tingting／190 | 94/100 | 36/50＝72% | 80/100＝80% |
| Eddy／175 | 80/100 | 12/50＝24% | 55/100＝55% |

声线和语速同时变化，不能分别归因，也不能外推真实客户。oracle中业务识别只有48%，说明在这份数据中，即便移除第一层错误，办理细分仍是明显瓶颈。

## 公平比较与耗时

在相同core子集、相同最终路由规则下重算旧设置：

| 设置 | 文本最终正确 | 音频最终正确 |
|---|---:|---:|
| 原独立两题，按当前业务规则评分 | 99/100＝99% | 134/200＝67% |
| 本轮两阶段串联＋办理专用题目 | 100/100＝100% | 135/200＝67.5% |

音频只多正确1条，不能称为有明确准确率收益。原全场景联合36.72%还包含额外28条语义用例和咨询功能标签，与本表口径不同。

本轮音频路由p50为153.35ms、p95为312.06ms；文本p50为174.73ms、p95为272.73ms。计入输入构造及实际执行的一到两个HTTP调用，不包含后续oracle。本次文本／音频路由随机交错，类别比例固定，题目也有变化；不是与上一轮两题必跑设置的受控性能收益认证。

## 工程结论

采用两阶段作为业务编排是合理的：接口更明确、只有需要时才付第二层计算成本、可分别评估和替换每层模型，并方便将来扩展第三类。实际产品仍由Go接受一次外部请求，在同一个进程内通过统一cgo封装按分支调用，不增加HTTP生产后端。

目前应把结论分开：**流程结构更适合；这套模型的直接音频业务识别尚未因此解决。** 低置信度或unknown如何进入澄清，需要单独校准和验收，不在本实验暗设阈值。后续优化应分别使用新开发集与未见验证集，保留原始音频和历史，不能只把第一层类别传给第二层而丢失用户诉求。

本轮没有实施生产Go串联，也没有更换服务SDK。合成音频局限和实际录音缺口见[原数据报告](../2026-10-28-banking-audio-v1/README.md)。
