# d1-2B 默认原生 ODS 验收

2026-10-28。用户要求核对Chinese比较后，把d1-2B设为默认并替换本机ODS供其他服务测评。本轮范围是**文字决策、Go＋cgo单进程、一次加载一个选定引擎**。不启用Omni媒体、多模型同时加载、自动降级或热切换。

## 原生一致性及协议

桥接固定d05706b llama.cpp兼容源码，复用官方 `server_decision_context` 的模板、输入转义、候选token分组、校准与readout；没有复制Chinese的模板、字母token或512分块。每题完整prompt一次8192上限physical batch，串行问题。d1 score按官方中位数。只链接决策计算库，不初始化任何C++ HTTP服务或监听器；Go仅通过C ABI调用同进程库。

最终带后端错误保护的库已重新跑完989条：自建427/504、TokSuite378/485，无请求错误；与之前官方实验接口的989个选择及全部候选概率**差异均为0**。银行最终158条共706次分类调用，完全复现既有d1文字成绩。Chinese对照697次调用，因门控预测不同，实际子调用数不同，不能比较调用总数当准确率。

两个旁路端口各12项协议检查通过，覆盖省略model默认d1、显式model、未知model404、拒绝音频／图像／视频、spoken question、超长输入、64问上限、40候选、多题保序和score中位数。生产路径目前只接受文字；模型名不被冒充为旧Chinese或Julia别名。

Go队列取消／Stop／Close回归和真实Metal A/B/A通过。原生错误回归通过：Metal/ggml ERROR会被锁存，返回runtime失败、不再输出决策；Go失败worker撤销ready并drain释放。初次并行两个d1预检触发Metal OOM，已经作废并保留在dist诊断；之后全部按单实例顺序运行。没有将故障概率或成功ready混入验收。

## 部署与复核

默认引擎改为d1-2b，保留显式Chinese／Julia。两者各绑定匹配ABI的固定SDK，一个进程只打开选定引擎，接入方式均为cgo。并未宣称完成此前设计的多模型注册表。普通无llama构建选d1会明确失败；Linux容器显式选Julia。

本机部署入口由 `scripts/deploy-local-d1.py` 管理：干净代码与同提交二进制先stage到独立release，备份两个旧launchd job；一个d1进程接管127.0.0.1:8080和18083。原Chinese job停用但配置及旧release保留，原Julia文件保留。新服务失败或可处理中断会尽力恢复两项旧服务，并核验原模型和就绪；两个恢复动作互不因第一项失败而跳过。

激活后核验两个端口同PID、model=d1-2b、真实推理、自包含release库；通过launchd正常停启后再次核验。实际激活结果另存 `activation.json`，代码及部署提交见该文件。恢复命令：`python3 scripts/deploy-local-d1.py rollback --release <activation记录的release目录>`。

原始响应在两个banking目录及accuracy目录；协议、实际加载库和工件身份也在本目录。`comparison.json`可离线复算：

```sh
python3 tests/evaluation/results/2026-10-28-d1-default/audit.py
```

Go全套／race／vet、Python46项及无GPU的C++后端错误回归通过。真实native测试需一次只启动一个d1实例，按 `internal/engine/d1/native_integration_test.go` 的环境开关运行。部署脚本回归仅使用临时目录与模拟命令，不改本机服务。

首次激活因launchd退出竞态未通过，原配置已自动还原、原两服务经直接bootstrap恢复并核验。`first-activation-failure.json`保留失败与恢复身份。无模型3秒延迟退出探针复现：bootout约0.004秒即返回，立即bootstrap退出5，等PID退出后成功。部署工具已增加PID退出等待、跨中断保留PID及登记清理短重试，四项部署回归通过。最终成功激活另见activation.json，不将首次失败当成功。
